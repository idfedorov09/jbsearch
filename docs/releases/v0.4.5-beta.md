# JB Search 0.4.5 pre-release preparation

This document describes a release candidate prepared on `dev`, not evidence
that it has been published. A later reviewed `dev` to `beta` pull request,
release authorization, and protected-environment checks remain separate steps.

## Changes since published pre-release 0.4.4

- Prepare both the VS Code Marketplace and Open VSX release workflows to
  publish six smaller, platform-specific VSIX packages for Windows, macOS, and
  Linux on x64 and ARM64, plus a universal fallback that retains all 12 existing
  ripgrep executables. The platform packages are intended to contain the one
  matching executable rather than the full universal inventory.
- Check all packages before uploading, publish and verify targets sequentially,
  and compare each registry's exact extension ID, version, platform, channel,
  and SHA-256. A duplicate skip alone does not count as a verified publication;
  a failed run can have already published some targets.
- Preserve the current branch, event, protected-environment, and authentication
  boundaries. Beta publication remains limited to eligible beta pushes, while
  the existing stable routes stay separate. The token route retains its HTTP
  credential guard; the separate Open VSX trusted route's existing limitation is
  documented in [the publishing guide](../open-vsx-publishing.md).

This is a compatible distribution change, not new Find/Replace functionality.
The main extension ID remains `idfedorov09.jbsearch`; the bundled client source
and protocol remain at version 0.1.0. Its package is rebuilt deterministically
for a release epoch without changing the source build identity.

## Version and channel

The proposed numeric version is **0.4.5**. At preparation on November 13, 2026,
0.4.4 was the highest public version in both registries and was marked
pre-release; stable 0.4.3 remained available. Neither registry exposed a 0.4.5
version in the public checks. Registry metadata can be delayed or change, so
repeat the checks before any release. The pre-release marker is stored in each
VSIX independently of the version number. A later stable release needs a
separate, higher numeric version under [the versioning policy](../versioning.md).

## Verification and limits

The preceding target-aware workflow change was tested locally using two
independent installations and matching stable and pre-release matrix digests;
its `dev` push also passed GitHub's Check and build-only platform workflows.
See [platform publication validation](../testing/platform-publication.md) for
that evidence. Past 0.4.4 package checks are not automatically evidence for
0.4.5.

On November 13, 2026, the 0.4.5 candidate passed `npm run check`, 988 automated
tests, and strict OpenSpec validation of 39 items. In a separate temporary source
copy, a clean `npm ci --ignore-scripts` was followed by `npm run package` and
both stable and pre-release `npm run package:matrix` builds. Each matrix verified
all seven artifact identities, targets, channels, native binaries, required
resources, and nested client. Pre-release archives ranged from 2,406,936 to
2,836,934 bytes for platform-specific targets; universal was 24,416,727 bytes.
The experiment used the pre-commit `dev` timestamp, not the timestamp or hashes
of any future `beta` publication. It did not upload to either registry.

A successful local build or GitHub Actions artifact does not prove registry
publication, gallery target selection, or a client update from an existing
universal package. Real Windows, macOS, and mixed-platform Remote acceptance
remain unverified. A wrong-host local VSIX was not reliably rejected in the
previous Linux test; use the artifact matching the workspace host or the
universal fallback. Actual publication must be checked per registry and target
and separately from platform runtime testing.
