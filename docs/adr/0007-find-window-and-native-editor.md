# ADR 0007: Отдельная Find Window, снимок результатов и настоящий редактор справа

Статус: **Accepted**

Дата: 2026-11-04

Размещение дерева и редактора пересмотрено в
[ADR 0008](0008-native-find-panel.md). Ниже сохранена история прежнего решения;
контракты snapshot/INVALID/замен продолжают действовать.

## Контекст

Пользователь авторизовал реализацию отдельного представления результатов,
приближенного к Find в IntelliJ IDEA: устойчивое дерево для последовательных
правок, редактируемый исходник справа, возврат к параметрам через шестерёнку и
обозначение переставших совпадать вхождений как INVALID. Перенос того же modal UI
во вкладку с формой запроса, нижним read-only preview и повторной кнопкой
Open in Find Window этому сценарию не соответствует.

Это решение уточняет [ADR 0003](0003-search-engine-and-session.md) и
[ADR 0006](0006-remote-preview-theme.md): компактный modal сохраняет собственный
TextMate preview и клиентский канал темы/grammars, а вкладка результатов получает
другой UI и настоящий TextEditor. Неудачная проба native preview внутри modal
из ADR 0006 не является доказательством невозможности редактора в обычной правой
editor group: для неё используется другой маршрут открытия и сохранения фокуса.

Требования и сценарии находятся в
[OpenSpec change implement-find-window](../../openspec/changes/implement-find-window/proposal.md).
Accepted означает принятое архитектурное решение и авторизованный scope;
результаты интеграционных проверок описываются отдельно от этого статуса.

## Решение

### Представление и жизненный цикл результатов

Find Window — отдельная центральная вкладка с кратким описанием запроса,
панелью действий и деревом «корень → каталоги → файл → вхождение». Она не
содержит повторной кнопки Open in Find Window, формы live-поиска и нижнего
read-only preview. UI использует цвета, шрифты и соглашения доступности VS Code.
Представление большого дерева виртуализируется; свёрнутые узлы и выбранное
вхождение определяются устойчивыми идентификаторами.

Завершённый поиск образует снимок: его query/options/scope и набор найденных
вхождений сохраняются до явного повторного запуска либо подтверждения новых
параметров. Начальная сортировка детерминирована по корню, пути и позиции.
`initialOrder` сохраняет место строки при последующих изменениях исходника.
Новые совпадения не подмешиваются автоматически, а исчезнувшие остаются INVALID.
Rerun Search формирует новый снимок с актуальным набором вхождений.

Позиции отслеживаются в UTF-16 через TextDocumentChangeEvent. После правки
известного документа его строки становятся pending, затем тот же поисковый
worker перепроверяет исходное условие, включая regex-контекст и captures.
Сопоставление по актуальным offset:length обновляет существующие вхождения;
отсутствие совпадения делает строку INVALID, не удаляя её. Undo может вернуть
валидность той же строки. Удалённый файл сохраняется как недоступный INVALID;
ошибка, timeout или неполная проверка оставляют явное непроверенное состояние.
Generation, версия документа и отмена исключают применение запоздавшего ответа.
Выражения не исполняются в extension host при отслеживании правок.

### Настоящий исходник справа

Пользователь просил разместить preview в Secondary Side Bar. В проверенных
stock VS Code 1.143.1 и 1.144.1 публичный API не предоставляет размещение
настоящего TextEditor в этой области: ViewColumn адресует editor grid, а
Secondary Side Bar содержит view containers. Внутренний AUX_WINDOW_GROUP
обозначает отдельное системное окно, а не эту панель. Не выдаём editor group
за sidebar и не обещаем буквальную поддержку недоступного размещения.

Принятая адаптация — отдельная **правая группа редактора** рядом с центральной
Find-вкладкой. Это явное отличие от буквального запроса; возможность настоящего
редактора в Secondary Side Bar остаётся за пределами этого решения и требует
нового API или другого отдельно принятого подхода.

Адаптер создаёт новую пустую группу справа через
`workbench.action.newGroupRight`, затем открывает исходный документ через
`window.showTextDocument`. `ViewColumn.Beside` для создания не используется:
он учитывает пользовательское направление открытия и может выбрать уже
существующую группу. Собственная группа отслеживается по TabGroup, а не по
захардкоженному номеру колонки. Пользовательские вкладки не переносятся и не
закрываются. При закрытии собственной группы следующий выбор безопасно создаёт
новую. Очередь навигации отбрасывает устаревшие запросы.

Выбор строки сохраняет фокус дерева через preserveFocus; явное действие
редактирования переводит фокус в TextEditor. Исходник использует обычные тему,
языковые расширения, сохранение и Undo VS Code. Изменения остаются несохранёнными
до обычного действия пользователя. Изменённая preview-вкладка сохраняется при
переходе к другому результату. Освобождение адаптера снимает свои декорации,
оставляя исходники и несохранённые вкладки открытыми.

Совпадения — native decorations поверх настоящего редактора. При открытии caret
сворачивается в начало диапазона; отдельная синяя text selection не перекрывает
подсветку. После правок обновляются только декорации, без повторного открытия,
прокрутки и перемещения caret. INVALID/pending не подсвечиваются как достоверные
совпадения. Цвета берутся из editor.findMatch* активной темы, а заливка сохраняет
70% исходной alpha через CSS color-mix. Цвета и opacity синтаксических токенов
не меняются. CSS-переменные рамок имеют явный fallback transparent. Зависимость
нативных декораций от theme CSS variables изолирована в адаптере и проверяется
при изменении поддерживаемых версий VS Code.

### Возврат к параметрам поиска

Шестерёнка открывает modal-draft с параметрами конкретной Find-вкладки и ссылкой
на неё. Правки draft не меняют параметры исходного снимка. Подтверждение без
New Tab обновляет исходную вкладку; Cancel/Esc сохраняет её параметры и выдачу.
Явный Open results in new tab создаёт независимую сессию. Shortcut поиска или
замены для активной Find-вкладки использует тот же маршрут, сохраняя связь с
исходным поиском. Файловые правки продолжают отслеживаться независимо от draft.

### Замены

Перед WorkspaceEdit необходимы актуальные проверенные диапазоны, captures,
версии и hashes содержимого. INVALID и pending не допускают одиночную замену;
Replace All блокируется, если набор содержит такие строки или выдача неполна.
Изменение содержимого либо версии между проверкой и применением не считается
успешной заменой. Поиск не сохраняет файлы автоматически, правки доступны обычному
Undo. После собственной замены снимок перепроверяется: строки не исчезают
самопроизвольно и при несовпадении становятся INVALID до Rerun Search.

## Рассмотренные альтернативы

1. **Повторно использовать modal UI во вкладке.** Сохраняет прежнюю архитектуру,
   но не даёт отдельного рабочего дерева и оставляет ненужные действия переноса.
2. **Native TextEditor в буквальной Secondary Side Bar.** В проверенном штатном
   API нет соответствующей цели размещения. Инъекция в DOM, патч VS Code или
   выдача WebviewView за полноценный редактор не принимаются.
3. **Встроить редактируемый Monaco в webview/sidebar.** Потребует отдельно
   согласовывать модель документа, dirty state, Undo, языковые возможности и тему.
   Настоящий редактор уже предоставляет эти свойства без такой эмуляции.
4. **Перезапускать весь поиск после каждой правки.** Новые строки и исчезновение
   старых нарушают устойчивый порядок при массовом редактировании и не позволяют
   показать INVALID на прежнем месте.
5. **Редактировать параметры исходного снимка прямо из modal.** Отмена не сможет
   сохранить исходные параметры; поэтому нужен отдельный draft с подтверждением.

## Доказательства и границы проверки

Изолированная проба адаптера 2026-11-04 выполнена в обычных desktop VS Code
**1.143.1** (`e646868227c3e3a9e3f24277c8c7220be42c0be7`) и **1.144.1**
(`261c84cb1eddf11235f9e2c921425e9663fbe556`), Linux/X11 через Xvfb и Playwright.
Использовались отдельные user-data/extensions directories и синтетические
исходники в `/tmp/jbsearch-find-preview-check`; рабочий профиль пользователя и
соседний BL-проект не менялись. После проверки процессы пробы завершены.

Подтверждены новая горизонтальная правая группа даже при
`openSideBySideDirection: down`, сохранение фокуса webview при навигации,
существующих dirty tabs и изменённого preview при переключении файла, обычные
редактирование/Undo, свёрнутый caret и обновление декораций без его перемещения.
В обеих версиях заливка сохранила alpha темы с множителем 0.7: исходные
`#ff000080` и `#00ff0066` дали вычисленные alpha 0.351373 и 0.28. Смена цвета
темы на `#0000ff40` дала 0.175686; foreground/opacity синтаксического токена
не изменились. При отсутствующей переменной рамки вычисленный border был
`rgba(0, 0, 0, 0)`. Итоговый набор адаптера содержит 13 unit-тестов; проверка
синтаксиса также прошла.

Это отдельная проверка адаптера и контракта размещения. Полный продуктовый прогон
дерева, draft, отслеживания INVALID и замен описан в
[протоколе Find Window](../testing/find-window.md), отдельно от этой пробы.
Результаты упаковки и актуальная матрица находятся в том же отчёте. Совместимость
macOS/Windows и Remote SSH между разными физическими машинами из Linux-пробы
не выводится. Временные исходные протоколы этой пробы:
`/tmp/jbsearch-find-preview-check/summary.json`, `adapter-results-1.143.1.json`,
`adapter-results-1.144.1.json` и `native-alpha-update-results*.json`.

## Последствия

Find Window имеет отдельный жизненный цикл и UI, поэтому controller должен
отделять live modal от сохранённой выдачи. Добавляются модель диапазонов,
перепроверка отдельных документов и небольшой адаптер native preview; новых
runtime-зависимостей не требуется. Общий правый preview следует за активной
Find-сессией, а независимые вкладки сохраняют свои параметры и снимки.

Нативный исходник избавляет Find Window от необходимости воспроизводить тему
и возможности языка в HTML. Это не отменяет TextMate-контракт компактного modal
из ADR 0006. Поставка остаётся стандартным расширением для обычного VS Code;
изменения серверного JavaScript подхватываются после Reload Window исходной
регистрации. Публикация, коммиты, версия и внешние действия в этот ADR не входят.
