# Публикация JB Search в VS Code Marketplace

В репозитории подготовлен `.github/workflows/publish.yml`. Его наличие в
рабочем дереве или `dev` само по себе не активирует выпуск: GitHub Actions
использует файлы коммита, а доверие и ограничения настраиваются отдельно.

## Разовая настройка пользователем

Сначала настройте ограниченное окружение, затем доверие издателя. Потребуются
права владельца репозитория GitHub и доступ к издателю `idfedorov09` в Marketplace.

### 1. Ограничить GitHub Environment

1. В GitHub откройте репозиторий `idfedorov09/jbsearch` → **Settings** →
   **Environments** → **New environment**. Создайте `marketplace`.
2. В **Deployment branches and tags** выберите **Selected branches and tags**.
3. Нажмите **Add deployment branch or tag rule**, выберите **Branch**, введите
   `master` и сохраните. Убедитесь, что нет других разрешающих правил.
4. Не добавляйте обязательных reviewers, если нужен полностью автоматический
   выпуск. Секреты в Environment для OIDC не нужны.

Одной проверки `master` внутри YAML недостаточно: недоверенная ветка может
содержать собственный вариант этого файла. Ограничение Environment нужно
настроить **до** предоставления workflow доверия в Marketplace. GitHub может
автоматически создать отсутствующее Environment без защиты, поэтому заранее
созданное и проверенное правило существенно.

### 2. Настроить доверие в Marketplace

1. Войдите под учётной записью, имеющей права на `idfedorov09`, в
   [кабинет издателя](https://marketplace.visualstudio.com/manage).
2. Выберите издателя **idfedorov09** → **Trusted Publishing** → **Create**.
3. Укажите:

   | Поле | Значение |
   | --- | --- |
   | Policy name | Например, `jbsearch-publish` |
   | Repository owner | `idfedorov09` |
   | Repository | `jbsearch` |
   | Workflow | `publish.yml` |
   | Environment | `marketplace` |

4. Сохраните политику. Имена должны совпадать с GitHub и файлом workflow.
   Персональный токен, GitHub Secret `VSCE_PAT` и Azure DevOps PAT не нужны.

Если доступ к издателю или нужным настройкам отсутствует, остановитесь и
выясните права; не создавайте другого издателя молча.

## Как происходит выпуск

После того как workflow находится в `master`, а обе настройки выше созданы,
push в `master` запускает проверки и при их успехе публикацию версии из
`package.json`. Job публикации работает на отдельном runner: после
`npm ci --ignore-scripts` он выполняет `npm run package`. Эта команда собирает
вложенный клиентский VSIX, упаковывает основное расширение и проверяет состав
пакета через `scripts/verify-package.js`, включая клиентскую часть и runtime-ресурсы.
Готовый проверенный VSIX передаётся в `vsce publish` через
`--packagePath ./*.vsix`; повторная упаковка исходников при публикации не выполняется.
Сборка из job проверок автоматически между runner не передаётся. В чистом runner
job публикации в корне находится один основной VSIX; клиентский лежит в `bundled/`.

Ручной запуск через GitHub Actions также разрешён только для
`master`. Повтор существующей версии пропускается: он **не обновляет** её
содержимое. Для нового выпуска заранее измените версию в `package.json` и
согласованном `package-lock.json`. Workflow не создаёт коммиты или теги.

**Push в `master` с новой версией после активации доверия может привести к
публичной публикации автоматически.** До переноса убедитесь, что исходники,
описание и поддерживаемые платформы готовы к выпуску; перенос и публикацию
согласовывают явно. CI собирает пакет сам; VSIX вручную загружать не нужно.
Локальные проверки workflow и упаковки не подтверждают настройку доверия или
успешный реальный выпуск; их результат фиксируется отдельно после согласованной публикации.

## Проверка после отдельно согласованного первого выпуска

- [ ] В GitHub Actions прошли job проверок и публикации нужного commit и версии.
- [ ] Карточка `idfedorov09.jbsearch` доступна и описание соответствует поставке.
- [ ] В чистом VS Code расширение устанавливается из Marketplace и запускается.
- [ ] Ручные проверки Find/Replace и платформ отмечены отдельно в
  [матрице тестирования](testing/find-replace.md).

Чтобы остановить будущие выпуски, пользователь может отключить workflow или
отозвать его политику доверия. Такие внешние действия не выполняются автоматически.
